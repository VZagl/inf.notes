# git-merge-to-build — Merge текущей ветки в build (стенд)

**Назначение:** При вызове `/git-merge-to-build` выполни merge **текущей** ветки (источник — любая, кроме `build`) в `build` с `--no-ff` и сообщением merge-коммита в формате Conventional Commits. Сгенерируй описание merge-коммита, покажи его пользователю и дождись подтверждения перед выполнением merge. Цель — осознанная выкладка на стенд GitHub Pages (push в `build` запускает deploy).

**Источники правил:** `docs/common/git-commit-description.md`, `docs/common/git-workflow.md`, `.github/workflows/deploy.yml`

---

## Алгоритм

### Шаг 1. Проверить текущую ветку

1. Выполни `git branch --show-current`.
2. Если текущая ветка — `build` — выведи: «Нельзя выполнить merge из ветки build. Переключитесь на исходную ветку (например develop или feature).» и заверши.
3. Если ветка не определена — выведи ошибку и заверши.
4. Запомни исходную ветку как `<исходная_ветка>` (источник merge).

### Шаг 2. Проверить целевую ветку `build`

1. Выполни `git fetch origin`.
2. Проверь наличие `build` локально и/или `origin/build` (`git branch -a`, Select-String / rg по `build`).
3. Если `build` **нет** ни локально, ни на remote:
   - Выведи предупреждение: «Ветка build не найдена. Для первого деплоя стенда её нужно создать (обычно от текущего состояния исходной ветки или develop).»
   - Спроси подтверждение на создание (как именно: `git branch build <исходная_ветка>` или от `develop` — уточни у пользователя при необходимости).
   - Без подтверждения — заверши. С подтверждением — создай локальную `build`, затем продолжай алгоритм (merge может оказаться fast-forward/пустым, если `build` уже указывает на тот же коммит — сообщи об этом).
4. Если `build` есть только на remote — при checkout она подтянется.

### Шаг 3. Обновить целевую ветку `build`

1. Выполни `git checkout build`.
2. Если есть `origin/build` — выполни `git pull origin build`.
3. Вернись на исходную ветку: `git checkout <исходная_ветка>`.

### Шаг 4. Сформировать сообщение merge-коммита

1. Выполни `git log <исходная_ветка> --oneline` и `git diff build..<исходная_ветка> --stat` (при отсутствии локальной истории — относительно `origin/build`, если применимо).
2. Если в `build` уже есть все коммиты исходной ветки (пустой diff) — сообщи: «Нечего мержить: build уже содержит изменения <исходная_ветка>.» и заверши без merge.
3. Проанализируй коммиты и изменённые файлы.
4. Определи type (fix, feat, refactor, chore и т.д.) и scope по правилам `docs/common/git-commit-description.md`. Для выкладки стенда без явного product-изменения допустим `chore` (например scope `deploy` / `pages`).
5. Создай заголовок: `type(scope): описание`.
6. В теле — маркированный список основных изменений из коммитов, попадающих в merge.
7. **Важно:** Описывать только изменения в коде проекта (исходный код, тесты, конфигурация). Не упоминать рабочие файлы memory-bank (activeContext.md, tasks.md, progress.md и т.д.).

### Шаг 5. Показать план и запросить подтверждение

1. Выведи: исходная ветка, целевая ветка (`build`), полное сгенерированное сообщение merge-коммита в блоке кода.
2. Напомни кратко: после merge для публикации на Pages нужен `git push origin build` (отдельным подтверждением, если пользователь согласится).
3. Спроси: «Выполнить merge ветки <исходная_ветка> в build с этим сообщением? Продолжить?»
4. Дождись явного ответа пользователя.
5. Если пользователь просит изменить сообщение — внеси правки, покажи обновлённое, снова спроси подтверждение. Повторяй до подтверждения.
6. Если пользователь отказывается — заверши без merge.

### Шаг 6. Выполнить merge (только после подтверждения)

1. Выполни `git checkout build`.
2. Создай `.git-commit-msg.txt` в корне проекта с полным текстом сообщения. **Кодировка:** UTF-8 без BOM. **КРИТИЧНО для Windows:** используй инструмент `Write` — он гарантирует корректную кодировку кириллицы. PowerShell-команды (`Out-File`, `[System.IO.File]::WriteAllText`) могут искажать кириллицу.
3. Выполни `git merge --no-ff <исходная_ветка> -F .git-commit-msg.txt`.
4. Удали `.git-commit-msg.txt`.

### Шаг 7. Проверить результат

1. Выполни `git log -1 --pretty=format:"%s%n%n%b"`.
2. Если сообщение отображается некорректно (кракозябры вместо кириллицы) — предложи исправить кодировку.
3. При подтверждении исправления:
   - Сохрани сообщение в `.git-commit-msg.txt` через `Write` (UTF-8 без BOM).
   - Выполни `git commit --amend -F .git-commit-msg.txt`.
   - Удали `.git-commit-msg.txt`.
   - Проверь: `git log -1 --format=%B` — кириллица должна отображаться корректно.
   - Выведи подтверждение об успешном исправлении.

### Шаг 8. Push (только по отдельному подтверждению)

1. Предложи: «Запушить `build` на origin? (`git push origin build` — запустит GitHub Pages deploy).»
2. Выполняй push **только** после явного согласия.
3. Не переключай пользователя обратно на исходную ветку без необходимости; можно предложить `git checkout <исходная_ветка>`.

---

## Не делать

- **Merge без подтверждения:** Никогда не выполнять merge до явного подтверждения пользователя.
- **Удаление веток:** Никогда не удалять и **не предлагать** удаление любой ветки (ни исходной, ни `build`, ни иных) в рамках этой команды.
- **Сообщение merge-коммита:** Не включать упоминания memory-bank (activeContext, tasks, progress и т.д.) — только изменения в коде.
- **Кодировка:** Не использовать PowerShell `Out-File` или `[System.IO.File]::WriteAllText` для `.git-commit-msg.txt` — только инструмент `Write`. UTF-8 без BOM.
- **Force push:** Не делать force push в `build`, `develop` или `main`.

---

## Важные замечания

- **Конфликты:** При конфликтах merge — сообщить пользователю, предложить разрешить вручную.
- **Роль `build`:** стенд для проверки, не замена `main` (релиз). Push в `develop` деплой не запускает; push в `build` или `main` — запускает (см. `deploy.yml`).
- **Источник:** любая ветка, кроме `build` (feature, `develop`, `main` и т.д.) — по выбору пользователя через текущий checkout.

## Чек-лист выполнения

- [ ] Текущая ветка определена и не является `build`
- [ ] Ветка `build` найдена или создана после подтверждения
- [ ] Целевая ветка `build` обновлена (fetch, pull при наличии remote)
- [ ] Есть что мержить (`build..<исходная_ветка>` не пуст)
- [ ] Сообщение merge-коммита сформировано по Conventional Commits
- [ ] В сообщении только изменения в коде, без memory-bank
- [ ] План показан, подтверждение на merge получено
- [ ] Файл `.git-commit-msg.txt` создан через `Write` (UTF-8 без BOM)
- [ ] Merge выполнен с `--no-ff` и `-F .git-commit-msg.txt`
- [ ] Файл `.git-commit-msg.txt` удалён
- [ ] Результат проверен (git log), кодировка корректна
- [ ] Удаление веток не предлагалось и не выполнялось
- [ ] Push на `origin build` — только после отдельного подтверждения (если запрошен)
- [ ] Итог выведен пользователю
