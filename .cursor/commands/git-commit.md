# git-commit — Генерация сообщения коммита

**Назначение:** При вызове `/git-commit` сгенерируй сообщение коммита на основе staged-файлов по правилам Conventional Commits. Покажи сообщение пользователю, дождись подтверждения и выполни коммит только после явного согласия.

**Источники правил:** `docs/common/git-commit-description.md`, `.cursor/rules/git.mdc`

---

## Алгоритм

### Шаг 1. Проверить наличие staged-файлов

1. Выполни `git status`.
2. Если нет staged файлов — сообщи об этом и заверши. Не добавляй файлы сам — пользователь добавит через `git add` при необходимости.
3. Выполни `git diff --staged`.
4. Если diff пуст — выведи «Нет файлов, добавленных для коммита.» и заверши.
5. **Принцип:** один коммит — одна логическая задача. Если staged-изменения нарушают это (несколько несвязанных задач, слишком крупный объём) — выведи предупреждение с кратким описанием, предложи варианты и дождись решения. Пользователь либо выбирает предложенный вариант (тогда выполни его), либо делает сам (тогда заверши):
   - **Дробить:** снять часть файлов из staged (`git reset HEAD <файл>`), сделать коммит оставшихся, затем добавить остальные и повторить `/git-commit`
   - **Продолжить как есть:** сформировать сообщение для всего объёма и выполнить коммит
   - **Отменить:** снять все из staged (`git reset HEAD`) и завершить без коммита

### Шаг 2. Сформировать сообщение коммита

1. Проанализируй изменения: что и зачем изменено.
2. При изменениях в `memory-bank/` примени правило «Приоритет type: memory-bank» из `docs/common/git-commit-description.md`.
3. **Определи ветку алгоритма:** **A — трекинг Memory Bank** (см. «Определение фазы» ниже) или **B — прочее** (`/build`, правки без трекинг-фазы).
4. **Ветка A (трекинг Memory Bank):** заголовок собирается **только** по формуле из раздела **«КРИТИЧНО: приоритет шаблонов Memory Bank»**; **не** применяй п.5; перейди к п.6.
5. **Ветка B (прочее):** заголовок = `type(scope): описание` по `docs/common/git-commit-description.md` (type и scope строчными, описание на русском, повелительное наклонение, до 50 символов).
6. Добавь тело: маркированный список изменений (прошедшее время, безличная форма, до 72 символов на строку). Для фаз Memory Bank — по «Принципам формирования тела» и шаблонам тела ниже.
7. При наличии задачи — футер: `Closes #123` или `Fixes #123`.
8. Полный формат — см. `docs/common/git-commit-description.md`.

#### КРИТИЧНО: приоритет шаблонов Memory Bank

Если коммит относится к **трекинг-фазе** Memory Bank (`/van`…`/close-task`, без прикладного кода в staged):

1. Заголовок собирается **только** по формуле ниже — **не** по общим правилам «type(scope): описание» из п.5 шага 2.
2. **Единственная** допустимая подстановка — `{task_id}` из `memory-bank/tasks.md`.
3. **Запрещено** менять шаблон: сокращать, опускать слова («задачу»), синонимы, «улучшения», подгонка под `git log`.
4. Ограничение «до 50 символов» **не применяется** — проверяется **только** соответствие шаблону из таблицы (подстановка `{task_id}`). Длину заголовка не проверять и не сокращать шаблон.
5. Примеры в разделе «Примеры полных сообщений» и старые коммиты в `git log` **не** отменяют таблицу шаблонов, если формулировка расходится с ней.

**Формула (трекинг-фазы):**

`docs(memory-bank): <строка из колонки «Шаблон заголовка» таблицы ниже, {task_id} заменён на значение из tasks.md>`

#### Шаблоны для фаз Memory Bank

**Источник `{task_id}`:** секция «Current Task» в `memory-bank/tasks.md` (приоритет 1) или «Last Completed Task» (приоритет 2, если Current пуст).

**Трекинг-фазы** (`/van`…`/close-task`, без прикладного кода) — type всегда `docs(memory-bank):`:

| Команда       | Шаблон заголовка                      |
| ------------- | ------------------------------------- |
| `/van`        | инициализировать задачу {task_id}     |
| `/plan`       | зафиксировать план задачи {task_id}   |
| `/creative`   | зафиксировать creative-фазу {task_id} |
| `/reflect`    | зафиксировать рефлексию {task_id}     |
| `/archive`    | заархивировать {task_id}              |
| `/close-task` | финализировать задачу {task_id}       |

**`/build`** — **не** `docs(memory-bank)`. Заголовок: `{type}({scope}): {описание по diff}`, где `type` — `feat`, `fix`, `refactor`, `test` и т.д. по смыслу изменений, `scope` — область фичи (модуль, компонент). Правки `memory-bank/tasks.md`, `progress.md`, `activeContext.md` в том же коммите не меняют type.

**Сателлиты `/close-task`:** при коммите после `/close-task` допустимы правки `docs/project/implementation-plan.md` (поле **Completed**) вместе с `memory-bank/**` — заголовок остаётся `docs(memory-bank): финализировать задачу {task_id}`.

#### Определение фазы (обязательно перед заголовком, ветка A)

Определи фазу по staged-файлам, `memory-bank/tasks.md` и `memory-bank/activeContext.md`. Если фаза **не** определена однозначно — **не** генерировать заголовок; спросить пользователя: «Какая фаза Memory Bank: /van, /plan, /creative, /reflect, /archive, /close-task?»

| Условие (staged + tasks.md / activeContext)                                                                           | Фаза          | Шаблон заголовка                      |
| --------------------------------------------------------------------------------------------------------------------- | ------------- | ------------------------------------- |
| Только `memory-bank/**` (и сателлиты по правилам выше), в tasks.md новый Current Task, статус содержит `VAN`          | `/van`        | инициализировать задачу {task_id}     |
| Только `memory-bank/**`, в tasks.md детальный план/чеклист BUILD, activeContext — режим PLAN или PLAN complete        | `/plan`       | зафиксировать план задачи {task_id}   |
| Только `memory-bank/**`, добавлен/изменён `memory-bank/creative/creative-*.md`, статус CREATIVE в tasks/activeContext | `/creative`   | зафиксировать creative-фазу {task_id} |
| Только `memory-bank/**`, добавлен/изменён `memory-bank/reflection/reflection-*.md`, REFLECT в activeContext           | `/reflect`    | зафиксировать рефлексию {task_id}     |
| Только `memory-bank/**`, добавлен/изменён `memory-bank/archive/archive-*.md`, ARCHIVE в progress/activeContext        | `/archive`    | заархивировать {task_id}              |
| `memory-bank/**` + карточка `completed-tasks/`, backlog, опционально implementation-plan **Completed**                | `/close-task` | финализировать задачу {task_id}       |

**Принципы формирования тела** (по истории коммитов в короткоживущих ветках):

1. **Первые пункты — содержательный итог фазы**, не перечисление «обновлён файл X».
2. **Правки Memory Bank объединять** в один пункт: «обновлены tasks.md, activeContext.md и progress.md» — если нет особой детализации по файлу.
3. **Конкретика из diff**: Level, ветка, ключевые решения плана, имя артефакта (`creative-*.md`, `reflection-*.md`, `archive-*.md`, путь `completed-tasks/…`).
4. **Переход фазы** — отдельный пункт в конце: режим BUILD, REFLECT→ARCHIVE, IDLE, следующий `/archive` / `/close-task` / `/van`.
5. **Не дробить** memory-bank на отдельные пункты по каждому файлу без причины.
6. **`/build`**: код, тесты, продуктовые docs — основные пункты; memory-bank **одной строкой в конце** (чеклист/прогресс), не как главный пункт.

**Шаблоны тела по фазам** (порядок пунктов; наполнение — из `git diff --staged`):

| Фаза          | 1-й пункт                                           | 2-й пункт                                                  | 3-й и далее                                                            |
| ------------- | --------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| `/van`        | постановка в tasks.md (Level, ветка, цель, чеклист) | уточнение backlog/scope, если менялся                      | объединённое обновление MB или next step                               |
| `/plan`       | суть плана в tasks.md (этапы, чеклист, риски)       | ключевые решения/ограничения из плана                      | activeContext (режим, next steps); сателлит implementation-plan        |
| `/creative`   | артефакт `creative-*.md` + ключевые решения         | статус CREATIVE COMPLETE, next steps в tasks/activeContext | —                                                                      |
| `/build`      | реализованное в коде/тестах/docs                    | детали по diff                                             | memory-bank одной строкой (опционально)                                |
| `/reflect`    | артефакт `reflection-*.md` + краткое содержание     | статус/Reflection Highlights в tasks.md                    | переход REFLECT→ARCHIVE в activeContext                                |
| `/archive`    | артефакт `archive-*.md` + что внутри                | tasks.md: Last Completed, резюме, /close-task              | progress, сброс activeContext                                          |
| `/close-task` | карточка `completed-tasks/YYYY/MM/{task_id}_….md`   | backlog (удаление, следующая задача)                       | tasks/progress/activeContext → IDLE; implementation-plan **Completed** |

### Шаг 3. Показать сообщение и запросить подтверждение

1. **Для ветки A (трекинг Memory Bank)** — перед сообщением коммита выведи блок проверки:

   ```
   **Проверка заголовка (трекинг Memory Bank):**
   - Фаза: `/van` (или другая из таблицы)
   - task_id: `…`
   - Шаблон из таблицы: `…`
   - Итог: `docs(memory-bank): …`
   - Совпадение с шаблоном (кроме task_id): да
   ```

   При «нет» — **не** показывать сообщение коммита; пересобрать заголовок по формуле.

2. Выведи сообщение в кодовом блоке (без обрамляющих ``` в итоговом тексте).
3. Спроси: «Выполнить коммит с этим сообщением? Продолжить?»
4. Дождись явного подтверждения («да», «ок», «выполни», «commit» и т.п.).
5. Если пользователь просит изменить — внеси правки, покажи обновлённое (с повторной «Проверкой заголовка» для ветки A), снова запроси подтверждение.
6. Если пользователь отказывается — заверши без коммита.

### Шаг 4. Выполнить коммит (только после подтверждения)

1. Сохрани сообщение (без обрамляющих ```) в `.git-commit-msg.txt` в корне проекта.
2. **Кодировка:** UTF-8 без BOM. **КРИТИЧНО для Windows:** используй инструмент `Write` — он гарантирует корректную кодировку кириллицы. PowerShell-команды (`Out-File`, `[System.IO.File]::WriteAllText`) могут искажать кириллицу.
3. Выполни `git commit -F .git-commit-msg.txt` (Shell с `required_permissions: ["all"]`).
4. Удали `.git-commit-msg.txt` (Shell с `Remove-Item .git-commit-msg.txt`).

### Шаг 5. Проверить результат

1. Выполни `git log -1 --pretty=format:"%s%n%n%b"` и выведи результат.
2. Если сообщение отображается некорректно (кракозябры вместо кириллицы) — предложи исправить кодировку.
3. При подтверждении исправления:
   - Сохрани сообщение в `.git-commit-msg.txt` через `Write` (UTF-8 без BOM).
   - Выполни `git commit --amend -F .git-commit-msg.txt`.
   - Удали `.git-commit-msg.txt`.
   - Проверь: `git log -1 --format=%B` — кириллица должна отображаться корректно.
   - Выведи подтверждение об успешном исправлении.

## Не делать

- **Коммит без подтверждения:** Никогда не выполнять коммит до явного подтверждения пользователя.
- **Кодировка:** Не использовать PowerShell `Out-File` или `[System.IO.File]::WriteAllText` для `.git-commit-msg.txt` — только инструмент `Write`.
- **UTF-8 с BOM:** Файл сообщения — только UTF-8 без BOM.
- **Смешение задач:** Не формировать коммит со смешением задач без предупреждения и явного выбора пользователя «продолжить как есть».
- **Изменение шаблона заголовка Memory Bank:** не сокращать, не перефразировать, не опускать слова из таблицы шаблонов.
- **git log как источник формулировки:** не копировать заголовки из истории, если они расходятся с таблицей шаблонов.
- **Слияние шаблона с общим правилом 50 символов:** для трекинг-фаз применяется только формула из раздела «КРИТИЧНО: приоритет шаблонов Memory Bank».

- [ ] Staged-файлы присутствуют, diff не пуст
- [ ] При нарушении принципа «один коммит — одна задача»: предупреждение выведено, варианты предложены, решение пользователя получено
- [ ] При изменениях в `memory-bank/` применён «Приоритет type: memory-bank»
- [ ] Определена ветка алгоритма: A (трекинг Memory Bank) или B (прочее)
- [ ] Для ветки A: фаза определена по таблице «Определение фазы» (или задана пользователем)
- [ ] Для ветки A: заголовок собран формулой `docs(memory-bank): <шаблон>` без изменения текста шаблона (подстановка только `{task_id}`)
- [ ] Для ветки A: в ответе выведен блок «Проверка заголовка» с полной строкой заголовка
- [ ] Заголовок **не** взят из `git log`, если тот не совпадает с таблицей шаблонов
- [ ] Тело коммита сформировано по «Принципам формирования тела» (содержательные пункты, без дробления MB по файлам)

- [ ] Добавлено тело с маркированным списком изменений (прошедшее время, безличная форма)
- [ ] Сообщение выведено в кодовом блоке
- [ ] Подтверждение пользователя получено
