# git-merge-to — Merge в develop (feature) или в main (из develop)

**Назначение:** При вызове `/git-merge-to` выполни merge с `--no-ff` и сообщением merge-коммита в формате Conventional Commits. Сценарии:

- **feature-ветка** → merge в `develop` (если `develop` нет — в `main`)
- **`develop`** → merge в `main`

Сгенерируй описание merge-коммита, покажи его пользователю и дождись подтверждения перед выполнением merge.

**Источники правил:** `docs/common/git-commit-description.md`, `docs/common/git-workflow.md`

---

## Алгоритм

### Шаг 1. Проверить текущую ветку и определить источник/цель

1. Выполни `git branch --show-current`.
2. Если ветка не определена — выведи ошибку и заверши.
3. Если текущая ветка — `main` — выведи: «Нельзя выполнить merge из ветки main.» и заверши.
4. Запомни исходную ветку как `<исходная_ветка>`.
5. Определи `<целевая_ветка>`:
   - если `<исходная_ветка>` = `develop` → `<целевая_ветка>` = `main`;
   - иначе (feature-ветка) → `<целевая_ветка>` = `develop` (с fallback на шаге 2).

### Шаг 2. Проверить целевую ветку (для feature → develop)

1. Если `<целевая_ветка>` уже `main` (сценарий develop → main) — переходи к шагу 3.
2. Выполни `git branch -a | Select-String 'develop'` (PowerShell) или эквивалент для текущей ОС.
3. Если `develop` не найдена — выведи предупреждение: «Ветка develop не найдена. Используется main как базовая ветка.» и установи `<целевая_ветка>` = `main`.

### Шаг 3. Обновить целевую ветку

1. Выполни `git fetch origin`.
2. Выполни `git checkout <целевая_ветка>`.
3. Выполни `git pull origin <целевая_ветка>`.
4. Вернись на исходную ветку: `git checkout <исходная_ветка>`.

### Шаг 4. Сформировать сообщение merge-коммита

1. Выполни `git log <исходная_ветка> --oneline` и `git diff <целевая_ветка>..<исходная_ветка> --stat`.
2. Проанализируй коммиты и изменённые файлы.
3. Определи type (fix, feat, refactor, chore и т.д.) и scope по правилам `docs/common/git-commit-description.md`.
4. Создай заголовок: `type(scope): описание`.
5. В теле — маркированный список основных изменений из коммитов ветки.
6. **Важно:** Описывать только изменения в коде проекта (исходный код, тесты, конфигурация). Не упоминать рабочие файлы memory-bank (activeContext.md, tasks.md, progress.md и т.д.).

### Шаг 5. Показать план и запросить подтверждение

1. Выведи: исходная ветка, целевая ветка (`develop` или `main`), полное сгенерированное сообщение merge-коммита в блоке кода.
2. Если цель — `main` (в т.ч. develop → main): кратко напомни, что push в `main` запускает деплой на GitHub Pages.
3. Спроси: «Выполнить merge ветки <исходная_ветка> в <целевая_ветка> с этим сообщением? Продолжить?»
4. Дождись явного ответа пользователя.
5. Если пользователь просит изменить сообщение — внеси правки, покажи обновлённое, снова спроси подтверждение. Повторяй до подтверждения.
6. Если пользователь отказывается — заверши без merge.

### Шаг 6. Выполнить merge (только после подтверждения)

1. Выполни `git checkout <целевая_ветка>`.
2. Создай `.git-commit-msg.txt` в корне проекта с полным текстом сообщения. **Кодировка:** UTF-8 без BOM. **КРИТИЧНО для Windows:** используй инструмент `Write` — он гарантирует корректную кодировку кириллицы. PowerShell-команды (`Out-File`, `[System.IO.File]::WriteAllText`) могут искажать кириллицу.
3. Выполни `git merge --no-ff <исходная_ветка> -F .git-commit-msg.txt`.
4. Удали `.git-commit-msg.txt`.

### Шаг 7. Проверить результат

1. Выполни `git log -1 --pretty=format:"%s%n%n%b"`.
2. Если сообщение отображается некорректно (кракозябры вместо кириллицы) — предложи исправить кодировку.
3. При подтверждении исправления:
   - Сохрани сообщение в `.git-commit-msg.txt` через `Write` (UTF-8 без BOM).
   - Выполни `git commit --amend -F .git-commit-msg.txt`.
   - Удали `.git-commit-msg.txt`.
   - Проверь: `git log -1 --format=%B` — кириллица должна отображаться корректно.
   - Выведи подтверждение об успешном исправлении.

## Не делать

- **Merge без подтверждения:** Никогда не выполнять merge до явного подтверждения пользователя.
- **Сообщение merge-коммита:** Не включать упоминания memory-bank (activeContext, tasks, progress и т.д.) — только изменения в коде.
- **Кодировка:** Не использовать PowerShell `Out-File` или `[System.IO.File]::WriteAllText` для `.git-commit-msg.txt` — только инструмент `Write`. UTF-8 без BOM.
- **Force push:** Не делать force push в `develop` или `main`.
- **Удаление develop — ЗАПРЕЩЕНО:** После merge `develop` → `main` **запрещено** предлагать и выполнять удаление ветки `develop` (локально и на remote): `git branch -d`, `git branch -D`, `git push --delete`, `git push origin --delete develop` и любые аналоги. Даже если пользователь просит удалить `develop` в рамках этой команды — отказать и пояснить, что `develop` — долгоживущая интеграционная ветка.

---

## Важные замечания

- **Конфликты:** При конфликтах merge — сообщить пользователю, предложить разрешить вручную.
- **Удаление ветки:** После merge feature → `develop`/`main` можно предложить удалить **feature-ветку** (история сохранится в merge-коммите). Выполнять удаление только с явного согласия пользователя. После merge `develop` → `main` удаление `develop` **запрещено** (см. «Не делать»).

## Чек-лист выполнения

- [ ] Текущая ветка определена, не `main`
- [ ] Исходная и целевая ветки определены (feature→develop|main или develop→main)
- [ ] Целевая ветка обновлена (fetch, pull)
- [ ] Сообщение merge-коммита сформировано по Conventional Commits
- [ ] В сообщении только изменения в коде, без memory-bank
- [ ] План показан (с напоминанием о деплое, если цель `main`), подтверждение получено
- [ ] Файл `.git-commit-msg.txt` создан через `Write` (UTF-8 без BOM)
- [ ] Merge выполнен с `--no-ff` и `-F .git-commit-msg.txt`
- [ ] Файл `.git-commit-msg.txt` удалён
- [ ] Результат проверен (git log), кодировка корректна
- [ ] Удаление feature-ветки — только предложено; при согласии пользователя выполнено
- [ ] После develop→main: удаление `develop` не предлагалось и не выполнялось (запрет)
- [ ] Итог выведен пользователю
