# git-merge-to-develop — Merge feature-ветки в develop

**Назначение:** При вызове `/git-merge-to-develop` выполни merge текущей feature-ветки в `develop` с `--no-ff` и сообщением merge-коммита в формате Conventional Commits. Сгенерируй описание merge-коммита, покажи его пользователю и дождись подтверждения перед выполнением merge.

**Источники правил:** `docs/common/git-commit-description.md`, `docs/common/git-workflow.md`

---

## Алгоритм

### Шаг 1. Проверить текущую ветку

1. Выполни `git branch --show-current`.
2. Если текущая ветка — `develop` или `main` — выведи: «Нельзя выполнить merge из ветки develop/main. Переключитесь на feature-ветку.» и заверши.
3. Если ветка не определена — выведи ошибку и заверши.

### Шаг 2. Определить целевую ветку

1. Выполни `git branch -a | Select-String 'develop'` (PowerShell) или эквивалент для текущей ОС.
2. Если `develop` не найдена — выведи предупреждение: «Ветка develop не найдена. Используется main как базовая ветка.» и используй `main` вместо `develop`.

### Шаг 3. Обновить целевую ветку

1. Выполни `git fetch origin`.
2. Выполни `git checkout develop` (или `main`).
3. Выполни `git pull origin develop` (или `main`).
4. Вернись на исходную ветку: `git checkout <исходная_ветка>`.

### Шаг 4. Сформировать сообщение merge-коммита

1. Выполни `git log <текущая_ветка> --oneline` и `git diff develop..<текущая_ветка> --stat` (или `main..<текущая_ветка>`).
2. Проанализируй коммиты и изменённые файлы.
3. Определи type (fix, feat, refactor, chore и т.д.) и scope по правилам `docs/common/git-commit-description.md`.
4. Создай заголовок: `type(scope): описание`.
5. В теле — маркированный список основных изменений из коммитов ветки.
6. **Важно:** Описывать только изменения в коде проекта (исходный код, тесты, конфигурация). Не упоминать рабочие файлы memory-bank (activeContext.md, tasks.md, progress.md и т.д.).

### Шаг 5. Показать план и запросить подтверждение

1. Выведи: текущая ветка, целевая ветка (develop/main), полное сгенерированное сообщение merge-коммита в блоке кода.
2. Спроси: «Выполнить merge ветки <текущая_ветка> в develop с этим сообщением? Продолжить?»
3. Дождись явного ответа пользователя.
4. Если пользователь просит изменить сообщение — внеси правки, покажи обновлённое, снова спроси подтверждение. Повторяй до подтверждения.
5. Если пользователь отказывается — заверши без merge.

### Шаг 6. Выполнить merge (только после подтверждения)

1. Выполни `git checkout develop` (или `main`).
2. Создай `.git-commit-msg.txt` в корне проекта с полным текстом сообщения. **Кодировка:** UTF-8 без BOM. **КРИТИЧНО для Windows:** используй инструмент `Write` — он гарантирует корректную кодировку кириллицы. PowerShell-команды (`Out-File`, `[System.IO.File]::WriteAllText`) могут искажать кириллицу.
3. Выполни `git merge --no-ff <текущая_ветка> -F .git-commit-msg.txt`.
4. Удали `.git-commit-msg.txt`.

### Шаг 7. Проверить результат

1. Выполни `git log -1 --pretty=format:"%s%n%n%b"`.
2. Если сообщение отображается некорректно (кракозябры вместо кириллицы) — предложи исправить кодировку.
3. При подтверждении исправления:
   - Сохрани сообщение в `.git-commit-msg.txt` через `Write` (UTF-8 без BOM).
   - Выполни `git commit --amend -F .git-commit-msg.txt`.
   - Удали `.git-commit-msg.txt`.
   - Проверь: `git log -1 --format=%B` — кириллица должна отображаться корректно.
   - Выведи подтверждение об успешном исправлении.

---

## Не делать

- **Merge без подтверждения:** Никогда не выполнять merge до явного подтверждения пользователя.
- **Сообщение merge-коммита:** Не включать упоминания memory-bank (activeContext, tasks, progress и т.д.) — только изменения в коде.
- **Кодировка:** Не использовать PowerShell `Out-File` или `[System.IO.File]::WriteAllText` для `.git-commit-msg.txt` — только инструмент `Write`. UTF-8 без BOM.
- **Force push:** Не делать force push в `develop` или `main`.

---

## Важные замечания

- **Конфликты:** При конфликтах merge — сообщить пользователю, предложить разрешить вручную.
- **Удаление ветки:** После merge можно предложить пользователю удалить feature-ветку (история сохранится в merge-коммите). Выполнять удаление только с явного согласия пользователя.

## Чек-лист выполнения

- [ ] Текущая ветка определена, не develop/main
- [ ] Целевая ветка (develop или main) определена
- [ ] Целевая ветка обновлена (fetch, pull)
- [ ] Сообщение merge-коммита сформировано по Conventional Commits
- [ ] В сообщении только изменения в коде, без memory-bank
- [ ] План показан, подтверждение получено
- [ ] Файл `.git-commit-msg.txt` создан через `Write` (UTF-8 без BOM)
- [ ] Merge выполнен с `--no-ff` и `-F .git-commit-msg.txt`
- [ ] Файл `.git-commit-msg.txt` удалён
- [ ] Результат проверен (git log), кодировка корректна
- [ ] Удаление feature-ветки — только предложено; при согласии пользователя выполнено
- [ ] Итог выведен пользователю
