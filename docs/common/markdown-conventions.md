> **Правила для людей и ИИ:** оформление Markdown-файлов в репозитории

# Соглашения по Markdown

Канонический документ для любых `.md` в репозитории (документация, спеки, трекинг задач, корневые README). Правила языка, домена и продуктовые соглашения — в `AGENTS.md` и `docs/project/` **этого** проекта; здесь только разметка и структура текста.

## Вертикальные пустые строки

- **Одна** пустая строка между смысловыми блоками: заголовок и следующий абзац, абзацы друг с другом, список и следующий заголовок, fenced code block и окружающий текст.
- **Не** вставлять пустую строку между соседними пунктами **одного** списка (`-`, `*`, `1.`).
- **Не** оформлять блок метаданных так, чтобы каждая строка была отдельным «разреженным» параграфом (пустая строка после каждой строки).

### Метаданные в несколько строк

Несколько полей вида `**Ключ:** значение` подряд — через перенос строки внутри одного блока (в конце строки — два пробела перед `\n`) **или** одним абзацем; выбрать один стиль и держаться его в файле.

**Правильно (плотный список, hard break):**

```markdown
## Раздел

- пункт один
- пункт два
```

**Правильно (метаданные с hard break):**

```markdown
**ID:** `task-1`  
**Статус:** в работе
```

**Неправильно (разреженный список):**

```markdown
- пункт один

- пункт два
```

## Заголовки и списки

- После заголовка `##` / `###` — один абзац или список; не дублировать пустыми строками внутри коротких секций без нужды.
- Вложенные списки — отступ по синтаксису CommonMark; между элементами **родительского** уровня пустых строк нет.
- Чеклисты `- [ ]` / `- [x]` — те же правила, что для маркированных списков.
- Плотный блок (метаданные, маркированный/нумерованный список, чеклист): соседние строки **без** пустой строки между ними; в конце каждой строки блока, **кроме последней**, — два пробела (hard break). Иначе Prettier при format on save часто снова вставляет пустые строки между пунктами.

## Таблицы и код

- Таблицы GitHub-flavored Markdown: строка заголовка, разделитель `|---|`, данные — без пустых строк между строками таблицы.
- Fenced blocks: язык после открывающих ` ``` ` при необходимости; одна пустая строка до и после блока, если блок не примыкает к заголовку по смыслу файла.

## Ссылки и пути

- Предпочитать **относительные** ссылки на файлы репозитория, согласованные с расположением текущего `.md`.
- Текст ссылки — осмысленный; голые URL в prose допустимы, если так принято в файле-образце рядом.

## Правки существующих файлов

- Сохранять принятый в **этом файле** ритм пустых строк и стиль метаблоков; не переписывать файл целиком без явной задачи на реструктуризацию.
- Точечные правки предпочтительнее полной замены содержимого.
- После заметных изменений применить форматтер Markdown проекта, если он настроен (например Prettier в `lint-staged`).

## Образец в репозитории

Перед созданием или крупным обновлением `.md` открыть **уже существующий** файл той же роли (соседний в каталоге или шаблон из документации проекта) и повторить плотность списков и метаданных, а не выдумывать новый стиль.

## Чеклист самопроверки (ИИ)

Перед сохранением или предложением diff по `.md`:

- [ ] Между пунктами одного списка нет лишних пустых строк
- [ ] У плотных метаблоков и списков: в конце каждой строки блока, кроме последней, два пробела (hard break); после format on save пункты не должны «разъехаться»
- [ ] Метаблоки не «разрежены» (не каждая строка через пустую строку)
- [ ] Между `##` / `###` и содержимым — не больше одной пустой строки подряд без причины
- [ ] Таблица и fenced block без разрывов внутри логических строк
- [ ] Стиль согласован с образцом в том же каталоге или шаблоном проекта
- [ ] Нет лишних пустых строк в конце файла (достаточно одного завершающего перевода строки)
- [ ] Пройден чеклист **не** заменяет чтение `AGENTS.md` и проектных правил для содержания текста
