# AGENTS.md - Настройки для AI помощников

## Структура docs

- `docs/common/` — общие правила, которые можно переиспользовать между проектами (например: `git-commit-description.md`, `dev-environment.md`).

- `docs/project/` — настройки, специфичные для этого проекта (например: `project-structure.md`, `tech-stack.md`, `testing-guidelines.md`).

## Источник правил

- **Все правила для AI‑помощников в рамках этого репозитория задаются в этом файле (`AGENTS.md`).**
- Личные `User Rules` пользователя не должны противоречить этому файлу.
- Если для другого проекта нужны другие правила, они должны быть оформлены в его собственном `AGENTS.md`.

## Язык правил

- **Правила в этом файле и во всех файлах правил, на которые есть ссылки в этом файле, могут быть написаны на любом языке** (английский, русский, смешанно и т.д.).
- Это намеренное решение по следующим причинам:
  - ИИ лучше понимает английский язык, поэтому некоторые правила оставлены на английском для точности формулировок;
  - Некоторые правила взяты из других источников (например, Memory Bank System) и оставлены на оригинальном языке, чтобы не исказить смысл;
  - Memory Bank System и связанные инструкции полностью на английском языке.
- **ИИ обязан понимать и следовать правилам независимо от языка их формулировки**, включая правила из всех файлов, на которые есть ссылки в этом файле (`docs/common/`, `docs/project/` и т.д.).
- Язык правила не влияет на его приоритет или обязательность выполнения.

## Правила работы

### Язык общения

- **ВСЕГДА отвечать на русском языке**, кроме случаев, когда пользователь использует фразы типа:
  - "ответь на английском"
  - "respond in English"
  - "use English"
  - Или другие явные указания на другой язык

- **Все текстовые элементы на русском языке**:
  - Объяснения логики кода
  - Комментарии в коде
  - Сообщения об ошибках (переводить и объяснять)
  - Примеры кода (с русскими комментариями)
  - Объяснения при рефакторинге

- **Строгая русификация вывода**:
  - Весь генерируемый текст должен быть на русском: пояснения, сообщения об ошибках, комментарии, подписи и строки в тестах (`describe`, `it`, `test`), а также пользовательские тексты UI.
  - **Исключения**: синтаксис языка, имена файлов, библиотек, классов, функций, переменных и ключевые слова языков/фреймворков.
  - Если контекст склоняет к английскому (например, Jest/React), принудительно переводить на русский.

**Примеры правильного/неправильного оформления:**

❌ **Неправильно** (английский язык в тестах):

```typescript
describe('Rendering', () => {
	it('should render footer element', () => {
		// test code
	});
});
```

✅ **Правильно** (русский язык в тестах):

```typescript
describe('Рендеринг', () => {
	it('должен отрендерить элемент footer', () => {
		// код теста
	});
});
```

- **Названия переменных/функций/классов** оставлять на английском языке

### Использование MCP и Context7

- **Context7 следует использовать автоматически, без дополнительного запроса от пользователя**, когда:
  - требуется генерация кода;
  - нужны шаги по настройке/конфигурации;
  - необходима документация по библиотекам или API.

- **При необходимости документации по библиотеке** (определяется автоматически ИИ на основе запроса пользователя):
  - сначала через Context7 определить идентификатор библиотеки;
  - затем получить её документацию/справку через MCP‑инструменты.

**Примечание**: Правила могут быть на любом языке (см. раздел "Язык правил").

### Логика рассуждений (sequential thinking)

- When the user explicitly writes "use sequential-thinking", the assistant must follow a structured, step-by-step reasoning and planning process before generating or editing code, and clearly reflect this process in its response.

- **Дополнительно, при сложных задачах** (определяется по следующим критериям):
  - Задача затрагивает архитектуру системы (изменение структуры проекта, паттернов, архитектурных решений);
  - Существует несколько (2+) различных подходов к решению задачи;
  - Задача требует изменения 3+ файлов одновременно;
  - Задача требует создания новых компонентов/модулей/сервисов;
  - Задача связана с интеграцией внешних систем/API.

  В таких случаях ассистент:
  - применяет последовательное, структурированное рассуждение даже без явного ключевого слова;
  - сначала кратко формулирует план шагов, затем действует по этому плану.

### Работа с командной строкой и ОС

- Перед выполнением консольных команд ассистент обязан:
  - учитывать указанную в контексте операционную систему и shell (например, Windows + PowerShell);
  - подбирать команды и синтаксис, совместимые с этой средой;
  - **Windows + PowerShell:** использовать `;` для цепочки команд, а не `&&` (в PowerShell 5.x `&&` не поддерживается). Подробнее: `docs/common/dev-environment.md`.

- **Если команда кроссплатформенная, но реализуется по‑разному** (например, в `bash` и `powershell`):
  - **По умолчанию**: давать адаптированный вариант для текущей ОС (указанной в контексте).
  - **Исключение**: если команда критически важна или может привести к ошибке, явно указывать различия и нужный вариант команды для каждой ОС.

- **Выполнение команд:** выполнять команды по одной; проверять результат каждой перед выполнением следующей.

### Подтверждение изменений

**КРИТИЧЕСКИ ВАЖНО**: Ассистент ОБЯЗАН показывать план изменений и запрашивать подтверждение перед внесением ЛЮБЫХ изменений в файлы, за исключением случая, когда пользователь ЯВНО указывает на выполнение БЕЗ подтверждения.

#### Инструменты, требующие подтверждения

Перед использованием ЛЮБОГО из следующих инструментов редактирования файлов требуется показать план изменений и дождаться явного подтверждения:

- `search_replace` / `ApplyPatch` / `edit_file` / `Write` / `edit_notebook`
- Любые другие инструменты, которые изменяют содержимое файлов

#### Когда требуется подтверждение

**Подтверждение требуется ВСЕГДА** для всех запросов, подразумевающих изменение файлов или каталогов, независимо от формулировки запроса.

**Правило**: Ассистент ОБЯЗАН спрашивать подтверждение ВО ВСЕХ СЛУЧАЯХ изменения файлов или каталогов, КРОМЕ случая, описанного в разделе "#### Когда подтверждение НЕ требуется".

**Без рассуждений, без интерпретаций, без "я подумал" или "пользователь согласился" — только буквальное следование правилу.** Если нет явного указания "без подтверждения" → ждать подтверждения.

#### Когда подтверждение НЕ требуется

Без подтверждения разрешается ТОЛЬКО:

- Читать файлы (`read_file`, `grep`, `list_dir` и т.п.)
- Выполнять команды для получения информации (`git status`, `git diff` и т.п.)
- Предлагать изменения в виде текста/патча в ответе, но НЕ применять их к файлам
- **Единственное исключение для изменений файлов**: Пользователь ЯВНО указывает на выполнение БЕЗ подтверждения, используя фразы типа:
  - "выполни без подтверждения"
  - "сделай сразу, без вопросов"
  - "примени немедленно, без подтверждения"
  - "внеси изменения без подтверждения"
  - Или другие явные указания на отсутствие необходимости подтверждения

**Важно**: Все остальные запросы, подразумевающие изменение файлов или каталогов, требуют подтверждения, независимо от формулировки. **Без исключений, без интерпретаций.**

#### Процесс подтверждения

Перед применением изменений ассистент ОБЯЗАН:

1. **Показать план изменений**:
   - Какие файлы будут изменены
   - Что именно будет изменено (краткое описание)
   - При необходимости показать diff или пример изменений

2. **Явно спросить подтверждение**:
   - Использовать фразы типа: "Применить эти изменения?", "Продолжить?", "Внести изменения?"
   - Дождаться явного ответа пользователя (да/нет/ок/применить и т.п.)

3. **Только после подтверждения** применять изменения

**Без рассуждений, без интерпретаций — только буквальное следование правилу.**

#### Примеры правильного поведения

✅ **ПРАВИЛЬНО** (вопрос требует подтверждения):

```
Пользователь: "что нужно изменить в правилах, чтобы ты генерировал docs(commit):?"

Ассистент: "Нужно добавить раздел про выбор scope. Вот план изменений:
- Добавить раздел 'Выбор scope' после раздела 'Формат сообщения'
- Добавить примеры scope для документации
- Добавить конкретный пример docs(commit):

Применить эти изменения?"
[ЖДЁТ ПОДТВЕРЖДЕНИЯ]
```

✅ **ПРАВИЛЬНО** (запрос на действие требует подтверждения):

```
Пользователь: "исправь баг в компоненте X"

Ассистент: "Вот план исправления бага:
- Файл: app/components/X.tsx
- Строка 15: исправить логику валидации
- Строка 23: добавить обработку ошибки

Применить эти изменения?"
[ЖДЁТ ПОДТВЕРЖДЕНИЯ]
```

✅ **ПРАВИЛЬНО** (даже "внеси изменения" требует подтверждения):

```
Пользователь: "внеси изменения в файл X"

Ассистент: "Вот что будет изменено:
- Строка 5: заменить 'старое' на 'новое'
- Добавить функцию Y после строки 10

Применить?"
[ЖДЁТ ПОДТВЕРЖДЕНИЯ]
```

✅ **ПРАВИЛЬНО** (явное указание БЕЗ подтверждения):

```
Пользователь: "исправь баг в компоненте X, выполни без подтверждения"

Ассистент: [сразу применяет изменения через search_replace]
```

❌ **НЕПРАВИЛЬНО** (вопрос не требует немедленного действия):

```
Пользователь: "что нужно изменить в правилах?"

Ассистент: [сразу применяет изменения через search_replace]
```

❌ **НЕПРАВИЛЬНО** (запрос на действие требует подтверждения):

```
Пользователь: "как исправить эту ошибку?"

Ассистент: [сразу редактирует файл без показа плана]
```

❌ **НЕПРАВИЛЬНО** (даже "исправь" требует подтверждения):

```
Пользователь: "исправь баг в компоненте"

Ассистент: [сразу редактирует файл без показа плана и подтверждения]
```

**КРИТИЧЕСКИ ВАЖНО**: Правила из этого файла (`AGENTS.md`) имеют **приоритет** над инструкциями Memory Bank System. При использовании Memory Bank System необходимо следовать правилам, описанным в `docs/common/memory-bank-usage.md`, которые адаптируют систему под правила проекта.

### Приоритет правил

При конфликте правил применяется следующий приоритет (от высшего к низшему):

1. **Правило о подтверждении изменений** — имеет наивысший приоритет. Все изменения требуют подтверждения, кроме явного указания пользователя на выполнение без подтверждения.

2. **Правило о языке общения** — ответы всегда на русском, кроме явного указания пользователя.

3. **Правило о Context7** — автоматическое использование Context7 при необходимости.

4. **Правило о sequential thinking** — применяется при сложных задачах или явном указании пользователя.

5. **Правило о работе с командной строкой** — адаптация команд под текущую ОС.

**Примеры разрешения конфликтов:**

- Если Context7 требует генерации кода → сначала показать план изменений и спросить подтверждение (правило о подтверждении имеет приоритет).
- Если пользователь просит ответить на английском → ответить на английском (правило о языке общения имеет приоритет над правилом о русском языке).

### Обнаружение конфликтов правил

**КРИТИЧЕСКИ ВАЖНО:** При обнаружении противоречий между правилами из разных источников (cursor_commands, AGENTS.md, docs/, memory-bank и т.д.):

1. **НЕ выполнять задачу автоматически**
2. **Сообщить пользователю о конфликте:**
   - Указать источники конфликтующих правил
   - Показать противоречивые инструкции
   - Объяснить, почему это конфликт
3. **Дождаться уточнения от пользователя**, какое правило применить

**Пример обнаружения конфликта:**

```
❌ ОБНАРУЖЕН КОНФЛИКТ ПРАВИЛ

Источник 1: AGENTS.md (раздел «Настройки тестирования»)
- Правило: «Требуется максимально полное покрытие тестами…»

Источник 2: docs/project/testing-guidelines.md
- Правило: «В этом проекте тестирование не требуется.»

Не могу продолжить выполнение задачи.
Какое правило применить?
```

**Цель:** Поддержание непротиворечивости всех правил проекта, так как правила постоянно дополняются и пользователь не может отследить все противоречия вручную.
